# Errors and Problem Details

Public HTTP failures use RFC 9457 Problem Details. Branch on the HTTP status
and Proctor's stable `code`; treat human-readable `title` and `detail` as text
for operators or users, not as a machine interface.

```json
{
  "type": "https://proctor.sudosylabs.com/problems/exam.invalid",
  "title": "Invalid request",
  "status": 400,
  "detail": "The request is invalid.",
  "instance": "/api/v1/exams",
  "code": "exam.invalid",
  "request_id": "req_01J7YN7BR7R2BW0VWP2JEN8M4M",
  "fields": {
    "field": "title"
  }
}
```

The exact `type` URI is documentation, while `code` is the bounded value an
integration uses for program logic. Each endpoint page lists its possible
codes in **Stable error codes**.

## Code Grammar

Every code is `<domain>[.<subdomain>].<condition>`: lowercase segments
separated by dots, each segment `snake_case`. The domain names the resource
family, such as `exam`, `exam.attempt`, or `authentication.mfa`. The condition
is the last segment; when it is qualified, the qualifier comes first and the
condition word last, as in `revision_conflict` or `content_invalid`.

The condition determines the HTTP status:

| Condition word | Status |
| --- | --- |
| `invalid` | `400` |
| `denied`, `disabled` | `403` |
| `not_found` | `404` |
| `conflict` | `409` |
| `expired` | `410` |
| `rate_limited` | `429` |
| `internal` | `500` |
| `unavailable`, `busy` | `503` |

A condition equal to a word in the table, or ending in `_` and that word,
takes its status. Any other condition, such as `archived` or
`deadline_reached`, names a resource state that rejects the request and
returns `409`. A few codes are documented exceptions: credential failures in
the `authentication` domain return `401` or `403`,
`exam.attempt.continuity_invalid` returns `404` so an invalid credential
reveals nothing, and the routing-kernel codes below use their HTTP-defined
statuses.

## Handling Rules

- Parse a non-success response as Problem Details when its content type is
  `application/problem+json`.
- Use `status` for the broad transport outcome and `code` for the Proctor
  condition.
- Show `detail` and `fields` only after applying the same output-escaping rules
  as any other untrusted response data.
- Record `request_id` in a support trace, but do not attach credentials,
  answers, or raw request bodies.
- Treat an undocumented code as an unknown recoverable failure. Preserve the
  HTTP status behavior and do not crash or reinterpret it as success.

## Validation Failures

When `fields` is present, its keys identify invalid request fields and its
values explain the constraint. The object is optional: a client must still be
able to handle validation failure without field-level details.

Unknown JSON fields, multiple JSON values, and malformed input are failures.
A body larger than the route's limit returns status `413` with code
`request.too_large`, whichever operation received it. Fix the request rather
than retrying it unchanged.

Every operation may also return `404` with code `route.not_found` for an
unknown path, `405` with code `route.method_not_allowed`, with an `Allow`
header, for an unsupported method, and `500` with code `server.internal` for
an unexpected server fault. These kernel failures are not repeated in each
endpoint's list of stable codes.

## Retries

Retry only when both the operation semantics and failure permit it. For a
mutation, use its documented idempotency behavior before retrying after a
timeout or lost response. Authentication, authorization, validation, conflict,
and assurance failures generally require a state or user-action change first.

DPoP has one narrow retry branch: on `authentication.dpop.use_nonce`, retain
the replacement `DPoP-Nonce`, create a completely new proof, and retry only if
the operation is otherwise safe. `authentication.dpop.replayed` also requires
a new proof identifier; resending the rejected proof can never recover. A
revoked Desktop Registration or incompatible Desktop build requires a new
human or installation action, not a token refresh loop.

WebSocket protocol failures use typed protocol envelopes instead of HTTP
Problem Details after the connection is established. See [Realtime and Replay](./realtime.mdx).
