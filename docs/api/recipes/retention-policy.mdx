# Review and Enable Institution Retention

One Institution Retention Policy governs examination work, integrity evidence
and Submission Reviews, audit history, and temporary examination exports across
all server nodes. Cleanup starts disabled. Saving periods never enables it:
a system administrator must approve a fresh preview for the exact policy
revision with strong, recent interactive authentication.

This workflow provides server APIs. Broader administration and examination
interfaces belong to the future desktop client. Account deletion and general
personal-data export are separate, unimplemented capabilities.

## Complete the Examination Records

After a Sitting is Closed, resolve its Reviews and use
<Link to="/api/reference/complete-exam-sitting-records">Complete Sitting Records</Link>.
The separate `exam.records.complete` permission follows the existing Exam
Manager and scoped override rules. Every relevant Submission must have a
finalized Review or an explicit, reasoned waiver. A manager cannot waive their
own Submission or bypass an undecided Flag.

The completion event starts the examination retention clock. Newly accepted
integrity evidence makes the Sitting's completion stale, cancels pending grace,
and requires acknowledged completion again. The new completion restarts the
clock. An exact duplicate does not. Retired categories reject further evidence;
later completion cannot restore removed records.

## Configure the Policy

Read <Link to="/api/reference/get-retention-policy">Get Retention Policy</Link>
with a Session authorized for `retention_policy.view`. Retain the revision.
Use <Link to="/api/reference/replace-retention-policy">Replace Retention Policy</Link>
with a strong, recently authenticated system-administrator Session and a fresh
`Idempotency-Key`. Cookie transport also requires CSRF proof.

Send all seven periods. `candidate_notices` is optional and defaults to false:

```json
{
  "expected_revision": 1,
  "submission_retention_days": 0,
  "integrity_retention_days": 0,
  "browser_activity_retention_days": 0,
  "security_operational_retention_days": 0,
  "audit_retention_days": 0,
  "export_retention_days": 1,
  "deletion_grace_days": 7,
  "candidate_notices": false
}
```

This example preserves examination and audit records indefinitely while
configuring 24-hour exports and seven-day grace. Those two operational settings
are recommendations, not chosen examination retention periods. The institution
must select its own work, integrity, Browser Activity, security operational, and audit periods before approving cleanup.

Zero means no configured expiry or grace, never immediate deletion. Positive
periods are durations in 24-hour days. Work, integrity, Browser Activity, security operational, audit and grace settings
accept up to 36,500 days. Export retention accepts zero when unconfigured or a
finite period of **1 through 7 days**. Configure a positive export period before
creating an export. No operation silently shortens a configured period.

The policy, audit, and retry outcome commit together. An exact no-op preserves
revision, timestamps, and approval. Every actual settings change pauses cleanup
and cancels existing grace. A lost response can be retried with the same key
and document. On `retention_policy.revision_conflict`, reread and review the
current policy before submitting a new revision and key.

## Review the Preview and Approve Cleanup

Use <Link to="/api/reference/create-retention-preview">Create Retention Preview</Link>
with the current policy revision and an idempotency key. A preview lasts one
hour. It contains counts for work, integrity, Browser Activity, security operational, audit, and retirement receipts;
it contains no answers, evidence text, or private reasons.

<Link to="/api/reference/list-retention-records">List Retention Records</Link>
provides bounded examination eligibility pages. Each Submission contributes four category records: work, integrity, Browser
Activity and security operational. A page limit counts Submissions, so it can
return up to four times that many category records. Follow its opaque cursor unchanged.

Review the blockers before approving:

- Incomplete or stale Sitting completion prevents examination retirement.
- Preservation holds protect their exact Exam, Sitting, or Submission scope.
- Unconfigured periods preserve the affected category.
- Retained integrity protects supporting work until both periods allow it.
  Zero integrity retention can therefore preserve supporting work indefinitely.
- An export under construction temporarily protects its exact source categories.
- Shared published Exam materials keep their independent references.
- Unfinished or referenced audit, incomplete purge, and active export references
  can prevent audit or receipt expiry.

Use <Link to="/api/reference/change-retention-control">Change Retention Control</Link>
with `state: "enabled"`, the current control revision, current policy revision,
and fresh preview ID. This requires `retention_cleanup.manage`, a protected
system-administrator Session, strong recent authentication, and an idempotency
key. At least one examination or audit period and positive grace must be
configured. Every worker rechecks live policy and dependencies; a preview is
not a frozen deletion command.

## Grace, Holds, and Notices

Eligible records receive positive grace before retirement. Seven days is the
recommended starting point. Use the control operation with `state: "paused"`
to stop new retirement. A policy change, hold, new export source protection, or
stale completion cancels the affected grace; resumed eligibility starts fresh
grace rather than reusing an old deadline.

<Link to="/api/reference/create-retention-hold">Create a Preservation Hold</Link>
for an Exam, Sitting, or Submission with `exam.records.hold` through the manager
or scoped override path. Holds also cover later records in that scope and do
not expire automatically. A strong, recently authenticated system administrator
must <Link to="/api/reference/release-retention-hold">release the hold</Link>
with `retention_hold.release` and a recorded reason. A hold racing retirement
either protects the record first or reports material already retired. It cannot
restore data; broader holds still protect remaining descendants.

Scheduling creates durable notices for responsible Exam Managers and active
institution operators in the same transaction as grace. Candidate notices are
opt-in. <Link to="/api/reference/list-retention-notices">List My Retention Notices</Link>
returns only the current Session User's notices, including cancellation and
mail-delivery state. It grants no examination access and does not acknowledge
that a message was read.

Mail preparation, queue, or SMTP failures remain visible without indefinitely
blocking cleanup. A cancellation invalidates the notice date; a queued stale
notice is suppressed before sending. An SMTP operation already started can
finish. Retention and byte cleanup are proposed hourly; notice expansion is
proposed every ten minutes, with durable retries after failures.

## Retirement and Physical Cleanup

The retirement transaction is the irreversible boundary. It removes private
category records, expires the corresponding retry copies, prevents ordinary
reads and late ingestion, and leaves permanent retirement markers. All four examination categories retire independently. Browser and native
operational retirement preserve separate Review evidence copies; integrity
retirement removes those copies and prevents new integrity intake. A work-only
read after integrity retirement
reports `integrity_state: "retired"` and `integrity_retired_at`, with the old
counters absent. Shared published Exam
materials are preserved.

Minimal receipts contain identifiers, dates, and state. They and audit history
follow the configured audit period from their own event, with positive grace.
Zero preserves them indefinitely. Unfinished work and durable references remain
explicit blockers. Eligible detailed cleanup audit can expire without being
kept forever solely by its own receipt. Permanent retirement markers survive
receipt expiry so expired records cannot become readable again.

Physical removal is separate and retryable. A backend delete acknowledgement
is insufficient: the server subsequently checks the exact current object key
for absence. If a writer's completion is unknown, that key remains under repeat
reconciliation and is still reported as pending, even after one absence
observation, because a delayed write could appear later.

Verified current-key absence does **not** certify secure media erasure,
termination of an already-open download, or removal from backups, snapshots,
historical object versions, or operator-managed replicas. Operators must manage
those copies and their own backup lifecycle separately. These status labels
make no broader erasure guarantee.

## Exports and Other Cleanup

Use the <Link to="/api/recipes/exam-exports">examination export workflow</Link>
for explicit Submission or Sitting archives. Exports are requester-only,
verifiable, independently expiring copies. They are not automatic prerequisites
for deletion. Downloads, retries, and later holds do not extend their lifetime.

Operational token, upload-lease, abandoned-stage, ordinary retry-outcome,
mail-history, and Job-history cleanup retain their own contracts. Institution
retention settings do not replace those security and maintenance lifetimes.
