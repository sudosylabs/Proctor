# Review Proctor Security

Security review starts with the decisions Proctor owns and the controls the
installation operator must supply. This guide maps the review surface without
replacing the detailed architecture contracts.

## Trust Boundaries

### Identity Establishes an Immutable Principal

Authentication proves the current <Term id="principal">principal</Term> and
assurance level. It does not pre-authorize a later action. Application use cases
re-read authoritative state and decide whether the principal may act on the
exact resource.

### Authorization Is Current and Scoped

<Term id="role">Roles</Term> and scoped <Term id="role-binding">Role Bindings</Term>
grant permissions. Academic relationships help define visibility and context,
but membership alone grants no unrestricted access.
Security-sensitive decisions are durably auditable and fail closed where the
architecture requires it.

<GovernedFigure asset="protected-request-assurance-flow" />

### PostgreSQL Is the Recovery Authority

Durable application state commits before disposable cache invalidation,
cross-node fan-out, or realtime publication. A cache or cluster message may be
discarded and reconstructed; it must never become the only record of a decision.

### Workspaces Are Durable; Execution Hosts Are Projections

<Term id="attempt-workspace">Attempt Workspace</Term> state remains under
Proctor's durable authority. An execution host receives a bounded, isolated
projection and can be repaired or revoked from authoritative state.

## Data-Handling Rule

Credentials, secrets, student data, exam answers, and unbounded user-controlled
content do not belong in ordinary logs or unsafe audit fields. Documentation,
examples, screenshots, and support reports must use synthetic data and preserve
that same boundary.
