# Configuration Reference

Proctor reads one versioned JSON document at process startup. This section
explains every supported field, its default, its accepted values, and the
relationships that validation enforces.

The defaults are a **local-development baseline**, not a production sizing or
security recommendation. In particular, the example uses loopback listeners,
development credentials, local storage, process-local cache, disabled mail,
and disabled execution.

## Start from the complete example

Copy the tracked example, protect the copy, and validate it before starting the
server:

```sh
cp config/config.example.json config/config.json
chmod 600 config/config.json
proctor config validate --config config/config.json
```

The canonical example is
[`server/config/config.example.json`](https://github.com/sudosylabs/Proctor/blob/main/server/config/config.example.json).
It contains every field and exactly matches the defaults compiled into the
server.

Proctor resolves the active file in this order:

1. the path passed to `--config`;
2. the path in `PROCTOR_CONFIG`;
3. `config/config.json` relative to the process working directory.

The server does not create the active configuration file.

## How loading works

Proctor begins with its compiled defaults and then decodes the JSON document
over them. An omitted field therefore keeps its default. This supports smaller
installation-specific files, but the complete example remains the clearest
starting point for operators and reviewers.

The decoder accepts exactly one JSON object and rejects unknown field names,
trailing JSON values, wrong value types, and malformed durations. Field names
are case-sensitive. Validation then checks individual bounds and cross-field
requirements before any runtime infrastructure is composed.

Durations use Go duration syntax, such as `250ms`, `15s`, `5m`, or `24h`.
Byte limits are integer byte counts. Network endpoints use `host:port` unless a
field explicitly requires an HTTP or HTTPS URL.

## Environment overrides

Supported `PROCTOR_` variables override the decoded JSON for the current
process. Overrides are validated together with the file, but they are never
written back to it. The generated
[environment variable inventory](./environment-variables.mdx) lists every
accepted variable and representation.

Keep credentials and key material in a protected secret-delivery mechanism.
Never commit populated examples. The active JSON file and any environment file
must be readable only by the Proctor service account or its protected group.

## Reload and restart boundary

Logging and the external-authentication provider registry are the only
configuration surfaces applied dynamically after a successful reload. Every
other change requires a process restart so listeners, infrastructure clients,
security policy, and the execution-host catalog remain coherent for the life
of the process.

Validate the intended effective configuration before reloading or restarting.
Validation proves the shape and relationships of the values; it does not prove
that PostgreSQL, Redis, SMTP, object storage, identity providers, or execution
hosts are reachable.

## Secret separation

Bootstrap credentials, MFA sealing keys, mail sealing keys, Memberlist keys,
TLS private keys, metrics bearer tokens, execution-host credentials, database
credentials, and object-storage credentials serve different trust boundaries.
Do not reuse material between them.

MFA, mail, and Memberlist rotations use one primary encryption key plus a
bounded fallback decryption ring. Roll the new primary to every relevant node,
retain the old key only while old ciphertext or cluster traffic can still
exist, and remove it after convergence. Proctor rejects reuse between the MFA,
mail, and Memberlist key purposes.

:::note[Production sizing status]

The repository does not yet define tested production sizing profiles for
connection pools, cache memory, request limits, file-content concurrency,
execution concurrency, or log queues. Use the enforceable ranges in this
reference, then determine production values from the installation's workload,
dependency capacity, and failure budget.
