# Configure Proctor and Protect Secrets

Proctor never generates or silently replaces the active deployment file.
Resolution order is explicit `--config`, then `PROCTOR_CONFIG`, then
`config/config.json` relative to the process working directory.

## Create and Validate the Active File

```sh
install -o root -g proctor -m 0640 \
  /opt/proctor/config/config.example.json \
  /etc/proctor/config.json

/opt/proctor/proctor config validate \
  --config /etc/proctor/config.json
```

Edit PostgreSQL, VFS, cache, mail, public URL, TLS, execution, authentication,
logging, and cluster settings for the selected topology. Validation rejects
unknown fields, unsafe listener combinations, malformed keyrings and addresses,
and cross-field conflicts without starting workers or listeners.

Read the checked [configuration reference](../reference/configuration.mdx) and
generated [environment inventory](../reference/environment-variables.mdx).

## Use Overrides Without Creating Drift

An environment override wins for that process and is never persisted back to
JSON. Store sensitive overrides in a protected environment file such as
`/etc/proctor/proctor.env` mode `0600`, or use the deployment secret mechanism
available in your environment. An empty variable is still a value and is
validated; it does not universally mean “unset.”

Record which source owns each effective value. Do not split one structured host
or provider entry across undocumented shell fragments. Execution host lists and
external provider objects remain reviewed structured JSON.

## Keep Purpose-Specific Secrets Separate

- bootstrap secret protects only pristine initialization;
- MFA and mail each use independent canonical base64 32-byte envelope keyrings;
- Memberlist uses its own 16/24/32-byte gossip keyring;
- public/metrics TLS private keys authenticate listeners;
- metrics bearer token protects remote scraping;
- execution-host token or client key authenticates one outbound host;
- PostgreSQL, Redis, S3, SMTP, and provider credentials belong only to their
  adapters.

Never reuse a key between purposes. Keep fallback decrypt keys only while old
data or nodes still require them. Configuration display and logs redact these
fields, but filesystem and secret-manager access remain operator responsibility.

## Know What Reloads

Logging and the external-provider registry can reconfigure dynamically after a
complete replacement validates. Listener, timeout, cluster, keyring, execution
host, and most infrastructure changes require restart. Validate first, change
one coherent deployment set, and verify readiness after restart.
