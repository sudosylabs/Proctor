# Operate Health, Metrics, Logs, and Traces

Process existence, liveness, readiness, and dependency diagnostics answer
different questions. Only readiness should put a node in the client traffic
pool.

<GovernedFigure asset="node-readiness-lifecycle" />

## Health Endpoints

| Endpoint | Meaning | Traffic decision |
| --- | --- | --- |
| `GET /health/live` | process and root runtime can answer | restart policy signal; not sufficient for routing |
| `GET /health/ready` | mandatory startup and serving prerequisites are currently satisfied | include/remove node from load-balancer pool |

Readiness remains false until platform dependencies, metrics, serving lease,
startup reconciliation, Jobs, WebSocket, listener, and HTTP handoff succeed. It
becomes false before drain. While serving, readiness also probes PostgreSQL,
the cache, the cluster transport, and VFS at most once per second, each probe
bounded to 2 seconds; a failed probe reports not ready until a later probe
succeeds, without stopping the process. The VFS probe checks only that the
local root directory or the S3 bucket exists, so its cost does not grow with
the number of stored files. A required metrics-listener failure, a
rejected serving lease, or a lease renewal that keeps failing past its retry
slack is terminal: Proctor removes readiness and stops serving rather than
risk operating without its durable node proof.

The serving lease lasts 30 seconds, renews every 5 seconds, and bounds each
operation to 5 seconds. A transient renewal failure is retried every second
while an attempt can still finish at least 5 seconds before the last renewed
lease expires, so a PostgreSQL interruption of roughly 15 seconds does not stop
the node. These are current implementation timings, not alert threshold
recommendations.

## Metrics

Metrics use a separate node-local listener, default `127.0.0.1:8067`, exposing
`GET /metrics` and, only when [profiling](#profiling) is enabled, the Go
runtime profiles. Scrape every node; Memberlist does not aggregate metrics.
The `proctor_` families cover readiness, HTTP, stores, caches, WebSocket,
cluster, Jobs, VFS, mail, and selected domain outcomes.

When binding beyond loopback, configuration requires static TLS and a random
32–512-byte bearer token. Keep the token in protected secret input. Do not put
it in scrape URLs or logs.

### Database Pool Saturation

Each node exports its PostgreSQL connection pool:

| Family | Meaning |
| --- | --- |
| `proctor_database_in_use_connections` | connections currently executing work |
| `proctor_database_idle_connections` | connections open and waiting in the pool |
| `proctor_database_open_connections`, `proctor_database_max_open_connections` | current and configured pool size |
| `proctor_database_waits_total` | requests that waited because every connection was in use |
| `proctor_database_wait_duration_seconds_total` | cumulative time spent waiting for a connection |

A rising `rate(proctor_database_waits_total[5m])` with in-use connections at
`Database.MaxOpenConnections` means the pool, not PostgreSQL, is the
bottleneck. Divide the wait-duration rate by the wait-count rate for the mean
wait. Compare the pool size multiplied by node count with PostgreSQL's own
connection limit before raising it.

### Slow Store Operations

Set `Database.SlowOperationThreshold` (for example `500ms`) to log one
`slow store operation` warning for every store operation that takes at least
that long. Each record names only the closed operation, such as
`user.get_by_email`, and `duration_ms`; it never includes SQL, arguments, rows,
or error text. The duration covers the whole named operation, including store
retries and every statement of a transaction. The record carries the
request's `request_id` and, with tracing enabled, the store span's `trace_id`.
The default `0s` disables
the log; `proctor_store_operation_duration_seconds` remains the aggregate view.

## Profiling

Set `Metrics.ProfilingEnabled` to serve Go runtime profiles from the same
listener under `/debug/pprof/` (`heap`, `goroutine`, `allocs`, `block`,
`mutex`, `threadcreate`, `profile`, `trace`, and `symbol`). Profiling requires
the metrics bearer token even on loopback, and it is never available on the
public listener. Fetch a profile from one node at a time:

```sh
curl --fail --silent --show-error --cacert metrics-ca.pem \
  --header "Authorization: Bearer $(cat metrics-token)" \
  --output node-a-cpu.pprof \
  'https://node-a.internal:8067/debug/pprof/profile?seconds=20'
go tool pprof -http=127.0.0.1:0 node-a-cpu.pprof
```

A CPU profile or execution trace must finish within `Metrics.WriteTimeout`
(default `30s`). Profiles describe code paths, stacks, and allocation sizes
rather than stored records, but treat captured files as internal diagnostics
and disable profiling again when the investigation ends.

## Logs

Use JSON logs for machine ingestion and bounded file rotation where local files
are selected. Preserve request/node correlation and closed component/outcome
fields. Do not increase diagnostic value by logging credentials, URLs with
secrets, User/Exam identifiers without approved purpose, Workspace paths or
content, recipients, evidence, provider payloads, or error strings as metric
labels.

Every record written while handling a request carries its `request_id`, the
value returned in the `X-Request-ID` response header. With tracing enabled,
records written inside a span also carry `trace_id` and `span_id`, so a log
search and a trace view lead to each other.

## Traces

Tracing is off by default. Set `Tracing.Enabled` and point
`Tracing.EndpointURL` at an OpenTelemetry collector's OTLP/HTTP traces
receiver, normally `http://127.0.0.1:4318/v1/traces` on the node itself or a
collector on its private network; use `https` when the collector is remote.
Proctor exports OTLP over HTTP with protobuf encoding rather than gRPC: it
needs no long-lived HTTP/2 client stream, passes ordinary HTTP proxies and TLS
termination, and keeps the gRPC transport out of the server.

To export directly to a hosted backend that authenticates OTLP requests, such
as Honeycomb or Grafana Cloud, set its `https` traces URL in
`Tracing.EndpointURL` and its credential in `Tracing.Headers`:

```json
"Tracing": {
  "Enabled": true,
  "EndpointURL": "https://api.honeycomb.io/v1/traces",
  "Headers": {"x-honeycomb-team": "<API key>"}
}
```

Header values are secrets. `proctor config show` prints each header name with
a `[redacted]` value, and values are never logged or recorded in spans. Prefer supplying them through `PROCTOR_TRACING_HEADERS`,
which uses the standard `OTEL_EXPORTER_OTLP_HEADERS` list format
(`name=value` pairs separated by commas, values percent-encoded) and replaces
the configured headers as a whole. Proctor itself ignores
`OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_EXPORTER_OTLP_TRACES_HEADERS`, so
configuration remains the only header source. Headers require an `https`
endpoint unless the collector is on loopback. A collector on the node or
private network can instead hold the backend credential itself.

Each node records:

| Span | Name | Attributes |
| --- | --- | --- |
| inbound HTTP request (server) | `GET /api/v1/users/{user_id}/affiliations`: method and route template | `http.request.method`, `http.route`, `http.response.status_code`, `proctor.request_id` |
| store operation (internal), only inside a sampled trace | `store user.get_by_email` | `db.system.name`, `db.operation.name` |
| Job execution (consumer, a new trace) | `job mail_delivery` | `proctor.job.type`, `proctor.job.outcome` |

Spans never carry request paths, query strings, headers, credentials, client
addresses, User or exam identifiers, SQL, arguments, rows, payloads, or error
text. A 5xx response, failed store operation, or failed Job is marked as an
error with only its status, `store operation failed`, or the outcome name. A
WebSocket upgrade's span ends at the handshake rather than lasting for the
connection.

Proctor continues an inbound W3C `traceparent` only when the connection peer is
in `Server.TrustedProxies`, the same rule that admits a proxy's request ID. Any
other client starts a new trace and cannot choose its identity or force
sampling; `baggage` is never read. `Tracing.SampleRatio` (default `1`) samples
new traces. Lower it on busy installations, since one request can produce many
store spans. The collector, not Proctor, owns retention, tail sampling, and the
trace backend. At shutdown Proctor flushes buffered spans for up to
`Tracing.ShutdownTimeout`; export failures are logged and never affect
requests or readiness.

The tracked development OpenTelemetry, Prometheus, Grafana, and Loki stack is a
local verification environment. It is not a production retention, sampling, or
alerting policy. `make run` and the cluster stack enable tracing and send spans
to the development collector, which prints one line per span in its log
(`make dev-logs`); it does not store traces.

## Diagnose a Not-ready Node

1. read the first bounded startup/runtime error from the node log;
2. verify effective configuration with `proctor config validate`;
3. verify PostgreSQL and selected required dependencies from their own trusted
   diagnostics without printing credentials;
4. compare `proctor version --json` and hosted build identity;
5. in a cluster, check stable Node ID, Redis/shared VFS, Memberlist key overlap,
   bind/advertise resolution, and compatible peer versions; and
6. fix the owning dependency or configuration, then restart and wait for
   readiness—never force the load balancer to ignore it.
