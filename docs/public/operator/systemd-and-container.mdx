# Run Proctor With Systemd or a Container

The repository ships two pre-production application runtime examples. Both run
one Proctor application node. Neither bundles a certified highly available
database, storage, cache, or load balancer.

## Systemd

The tracked `deploy/systemd/proctor.service` runs as the dedicated `proctor`
user, validates configuration in `ExecStartPre`, starts `proctor serve`, and
uses `Type=notify`.

```sh
install -o root -g root -m 0644 \
  /opt/proctor/deploy/systemd/proctor.service \
  /etc/systemd/system/proctor.service
systemctl daemon-reload
systemctl enable --now proctor
systemctl status proctor
```

The unit removes capabilities, enables `NoNewPrivileges`, protects system and
kernel surfaces, restricts address families, and grants only the state, log,
and runtime directories. Use a drop-in for another deliberate writable path;
do not weaken `ProtectSystem` or grant root merely to bind public ports. Let a
load balancer bind privileged ports or grant only the narrow OS bind capability
after reviewing the change.

Proctor sends `READY=1` only after dependencies, serving lease, startup
reconciliation, Jobs, WebSocket, listener handoff, and readiness succeed. A
notification failure is logged; systemd's startup timeout remains the external
boundary. Proctor also reports the rest of its lifecycle to systemd:

| Event | Notification |
| --- | --- |
| shutdown begins, after readiness is withdrawn | `STOPPING=1` |
| `SIGHUP` reload (`systemctl reload proctor`) | `RELOADING=1` with `MONOTONIC_USEC`, then `READY=1`, also after a failed reload that kept the running configuration |
| every half `WatchdogSec` while the node is healthy | `WATCHDOG=1` |

The tracked unit sets `WatchdogSec=60s`. Proctor samples its own readiness,
the same answer `/health/ready` gives including the bounded PostgreSQL, cache,
cluster, and VFS probe, several times per keep-alive interval and sends
`WATCHDOG=1` only when the node was ready at least once since the previous
keep-alive. A short dependency blip therefore costs nothing, but a node that
stays unready for most of a minute, or whose readiness check wedges, stops the
keep-alives; systemd then aborts it with `SIGABRT`, which writes every
goroutine's stack to the journal, and `Restart=on-failure` starts it again.
After `STOPPING=1` the keep-alives continue through the bounded drain, so
`TimeoutStopSec`, not the watchdog, limits shutdown. Raise `WatchdogSec` in a
drop-in if your PostgreSQL failover routinely takes longer than about half a
minute; `WatchdogSec=0` disables the watchdog.

The unit keeps `Type=notify` with `ExecReload` sending `SIGHUP`, which works
on every supported systemd. On systemd 253 or newer you may instead set
`Type=notify-reload` and remove `ExecReload`; systemd then sends `SIGHUP`
itself and waits for the same `RELOADING=1` and `READY=1` pair.

## Container

Copy the tracked `deploy/compose` example, select an immutable image tag and
digest, and provide protected config, environment, state, log, and secret paths.

```sh
docker compose config
docker compose up --detach --wait
docker compose ps
```

The application container runs uid/gid `65532`, drops all capabilities, uses a
read-only root filesystem, has a bounded no-exec `/tmp`, and mounts only the
declared writable data/log paths plus read-only configuration/secrets. Its
healthcheck calls the packaged `proctor-healthcheck` against readiness.

Do not bake populated configuration or secrets into the image. Do not mount the
Docker socket. The example's single-host service is a deployment illustration,
not active-active infrastructure.

## Shutdown

Send SIGTERM or use the runtime's normal stop command. Proctor first becomes
unready, drains HTTP, stops Jobs and WebSocket, closes transport, withdraws the
serving lease, closes metrics, flushes traces, then closes shared
infrastructure. One `Server.ShutdownTimeout` budget, measured from when
shutdown starts, bounds that whole sequence: every step that waits gets only
what remains of it, so a slow step shortens later steps instead of extending
shutdown. Keep `TimeoutStopSec` and the container stop window longer than
`Server.ShutdownTimeout` plus the logging flush (`Log.ShutdownTimeout`); the
tracked units already are.

A second SIGTERM or SIGINT during the drain forces the stop: remaining HTTP
connections close at once, the shutdown budget ends, so Jobs, WebSocket, and
metrics stop waiting for in-flight work, and the process exits with status 1 so the supervisor records an incomplete
drain. A third signal exits immediately without further cleanup; the serving
and discovery leases then expire on their own.
