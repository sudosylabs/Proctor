# Develop the Hosted Webapp

The private `webapp` package builds the React and Vite application served by
Proctor. Its current product surface is the bounded family of access and
onboarding pages: setup, sign-in, registration, Invitation acceptance,
password recovery, email verification, Desktop authorization, provider
connection, and terminal Session confirmation.

The browser owns presentation and interaction. It does not become an
alternative authority for routes, HTTP shapes, localization messages,
authentication policy, or durable application state. A complete feature
therefore consumes generated adapters, classifies remote outcomes into a small
feature state, and renders that state through components whose contracts
already match the behavior.

## Place Each Decision Once

| Decision | Owner |
| --- | --- |
| Which browser paths the server hosts | `server/webui/hosted_routes.json` |
| How each hosted route sanitizes bootstrap input and selects a page | `webapp/src/app/HostedRoutes.tsx` |
| Public request and response shapes | Human-owned YAML under `server/openapi` |
| Browser compile-time HTTP types | Generated `webapp/src/api/generated/schema.ts` |
| Same-origin credentials and CSRF transport mechanics | `webapp/src/api/client.ts` and `webapp/src/auth` |
| Which remote outcomes matter to one feature | The feature-owned API action |
| Feature state, validation, recovery, and visible copy selection | The owning feature and presentation module |
| Repeated domain-neutral interaction behavior | A shared component with a narrow adjacent contract |
| Visible English source messages | The `webapp.*` namespace under `server/i18n` |
| Product tokens and durable visual rules | `webapp/design-system/tokens.mjs` and `webapp/DESIGN_SYSTEM.md` |
| Reset and document defaults | `webapp/src/styles` |
| Feature and component styling | Colocated CSS Modules |

When two rows appear to own the same choice, stop and resolve the duplication.
For example, OpenAPI says which error codes an operation may return. The
feature action decides which of those codes produce the same safe visible
outcome. A presentation component receives that outcome; it does not compare
HTTP statuses or Problem Details itself.

## Work from States, Not from Screens

Before changing code, write a feature map:

~~~text
Purpose:          what task can the person complete?
Hosted route:     which server-owned path presents it?
Bootstrap input:  what sanitized, purpose-specific input reaches React?
API operations:   which generated operations are consumed?
States:           initial, loading, ready, empty, invalid, denied, unavailable,
                  pending, complete, and terminal states that can really occur
Recovery:         which state preserves values, retries, redirects, or stops?
Focus:            where does focus begin and move after each user action?
Copy:             which webapp.* messages are required?
Components:       which existing contracts apply, and what remains local?
Evidence:         which unit and browser tests prove behavior and presentation?
~~~

Do not start with a page mockup and then force every state into it. A loading
view may have no form. A terminal result may remove the invoking action and
move focus to a replacement heading. An ordinary submission failure should
usually preserve the fields, action position, and focus.

## Preserve the Browser Trust Boundary

The hosted webapp always addresses the Installation that served it. It has no
remote API-base option. Cookie credentials remain same-origin, unsafe methods
add the CSRF header when the server cookie is present, and sensitive fragment
credentials are removed from browser history before React renders.

The browser may improve guidance, but the server still validates input,
authenticates the principal, authorizes actions, and commits durable state.
Never render arbitrary server error text, infer permission from a hidden
control, or treat browser storage as an authority.

## Know the Live Authorities

This manual explains contributor tasks rather than duplicating every route or
component. During implementation, read:

- the [webapp package guide](https://github.com/sudosylabs/Proctor/blob/main/webapp/README.md);
- the [product design-system contract](https://github.com/sudosylabs/Proctor/blob/main/webapp/DESIGN_SYSTEM.md);
- the feature and component `CONTRACT.md` files beside the changed code;
- the reviewed OpenAPI YAML for public HTTP behavior;
- the server localization catalog for visible messages; and
- current unit and Playwright tests for executable evidence.
