# Trace a Complete Password-Reset Feature

This tutorial reads the existing `/account/reset-password` browser feature end
to end. It is a useful teaching slice because one small page crosses route
generation, a sensitive fragment credential, OpenAPI-generated types,
same-origin transport, field and form validation, terminal state replacement,
localization, shared components, unit tests, and three-engine browser tests.

The goal is to understand why each owner participates. Do not copy every file
for a feature that has no credential, form, terminal replacement, or API call.

## State the Behavior before Reading Code

The browser route receives one password-reset token in a URL fragment. Before
React renders, Proctor removes the complete fragment from history and projects
the value as a purpose-specific password-reset credential.

The ready form accepts a new password and a browser-only confirmation. A
successful request clears the credential and fields, replaces the form with a
completion task, announces the new state, and focuses its heading. An unusable
credential produces a different terminal task. Password-policy failure returns
focus to the password field; rate limiting and transport failure remain
recoverable form feedback.

The browser never renders or stores the token, sends the confirmation field,
or displays arbitrary server error prose.

| Concern | Owner |
| --- | --- |
| Hosted path | Server route catalog |
| Route membership type | Generated browser route adapter |
| Fragment sanitation and purpose type | Root hosted-route bootstrap |
| Public request, success, and errors | OpenAPI YAML |
| Compile-time request shape | Generated browser API schema |
| Accepted response and semantic result mapping | Feature API action |
| Values, validation, focus, announcements, and recovery | Reset-password content |
| Labels and messages | Server-owned `webapp.*` catalog and generated adapter |
| Repeated field, action, evidence, feedback, and task behavior | Shared component contracts |
| Assembled behavior and presentation | Vitest and Playwright |

## 1. Begin at the Server-Owned Route

Read [server/webui/hosted_routes.json](https://github.com/sudosylabs/Proctor/blob/main/server/webui/hosted_routes.json).
It includes `/account/reset-password` among the finite paths served by the
hosted application.

Run the route generator:

~~~sh
cd webapp
npm run routes:generate
npm run routes:check
~~~

The generated
[webapp/src/app/routes.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/app/routes.ts)
adds the literal path to `hostedRoutes`; the derived `HostedRoute` union then
forces authored browser behavior for that member. Never edit the generated
file.

## 2. Follow Credential-Safe Bootstrap

Read
[webapp/src/app/HostedRoutes.tsx](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/app/HostedRoutes.tsx)
and
[webapp/src/auth/fragments.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/auth/fragments.ts).

The authored descriptor declares:

- document title key `webapp.reset_password.document_title`;
- fragment policy `password_reset_token` with parameter `token`;
- a bootstrap projection whose credential has that exact kind; and
- the `ResetPasswordPage` renderer.

`captureFragmentCredential` removes the complete fragment with
`history.replaceState` before it parses the parameter. It accepts exactly one
non-empty value. A malformed fragment, extra parameter, or missing value
produces no credential.

This ordering matters. Sanitizing only after successful parsing would retain a
malformed secret in browser history. Passing a generic token object would make
cross-purpose credential misuse easier.

The root test suite verifies exact purpose typing, wrong-credential rejection,
and fragment removal for every credential-bearing route.

## 3. Read the Feature Contract and Thin Page

Read the
[reset-password contract](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/features/reset-password/CONTRACT.md)
before implementation.

The contract closes the credential lifetime, exact API operation, browser-only
confirmation, semantic failure mapping, persistent feedback, terminal
replacement, focus behavior, and sensitive-data exclusions.

[ResetPasswordPage.tsx](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/features/reset-password/ResetPasswordPage.tsx)
then performs only real dependency wiring:

- select the `single` access-shell variant;
- resolve the localized skip-link label;
- pass the sanitized token; and
- pass the real `completePasswordReset` action.

It does not own the form state or make the transport call during rendering.

## 4. Inspect the Public HTTP Contract

Read
[server/openapi/fragments/authentication/auth-password-reset.yaml](https://github.com/sudosylabs/Proctor/blob/main/server/openapi/fragments/authentication/auth-password-reset.yaml).

`POST /api/v1/auth/password-reset/complete` declares:

- public authentication classification and empty OpenAPI security;
- no idempotency-key protocol;
- a strict body with `token` and `password` only;
- HTTP 204 as the success response;
- bounded bad-request, rate-limit, and unavailable responses; and
- explicit password, token, recovery, request, and rate-limit error codes.

The password confirmation is absent because it is a browser interaction aid,
not server input. Expired, replayed, superseded, malformed, and concurrent-
loser credentials remain concealed behind a common unusable-token behavior.

If this contract changes:

~~~sh
make -C server openapi-build
make -C server openapi-agreement
cd webapp
npm run api:generate
npm run api:check
~~~

Review generated `PasswordResetCompletionRequest` and
`completePasswordReset` operation types in
[schema.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/api/generated/schema.ts).

## 5. Read the Feature API Action

Read
[ResetPasswordApi.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/features/reset-password/ResetPasswordApi.ts).

The action uses the shared typed client and sends only `{token, password}`. It
accepts exactly HTTP 204 as complete. Then it maps public errors into five
presentation-safe outcomes:

| Result | Meaning |
| --- | --- |
| `complete` | The declared no-content success occurred |
| `invalid` | The credential or request cannot be used safely |
| `password_rejected` | The replacement password failed server policy |
| `rate_limited` | Another attempt should wait |
| `unavailable` | Any unknown, malformed, unexpected, or transport failure |

The presentation never receives an HTTP status or Problem Details object. The
action never accepts arbitrary `title` or `detail` as interface copy.

Run its focused test:

~~~sh
cd webapp
npx vitest run src/features/reset-password/ResetPasswordApi.test.ts
~~~

The test proves exact success, every mapped public code, an unknown code, an
unexpected 2xx response, and rejected transport.

## 6. Follow the Feature State Machine

Read
[ResetPasswordContent.tsx](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/components/PasswordRecovery/ResetPasswordContent.tsx).

The visible state is deliberately small:

~~~ts
type ResetState = "ready" | "complete" | "invalid";
~~~

Pending and recoverable errors remain properties of the ready form rather than
pretending to be new route-wide states. The credential lives in one `useRef`
so it does not enter rendered output. Initial absence selects `invalid`
without a focus move.

Submission checks in document order:

1. ignore repeat activation or a missing credential;
2. require the password and focus it when empty;
3. require confirmation and focus it when empty;
4. compare the two browser values and focus confirmation on mismatch;
5. mark the form pending and clear obsolete errors;
6. call the feature action;
7. clear the credential and fields on complete or invalid terminal results;
8. replace the form, announce the heading, and focus it for that user-triggered
   transition;
9. return password-policy rejection to the password field; or
10. keep rate-limit and unavailable failure in persistent form feedback.

Edits clear only errors made obsolete by that edit. A recoverable transport
failure does not destroy the token or entered values.

## 7. Inspect the Shared Components

The ready state composes existing domain-neutral contracts:

- `AccessTaskIntro` for purpose, `h1`, and supporting context;
- `PasswordField` for label, required semantics, adjacent guidance, error
  association, and named disclosure control;
- `Notice` for stable Session-revocation evidence;
- `Button` for explicit submit and pending behavior; and
- `FormFeedback` for the persistent action-adjacent failure lane.

Terminal states use `TaskStateAnnouncement`, `TaskState`, `Notice`, and
`TaskStateActions`. Their shared contracts define hierarchy, announcement, and
responsive action behavior; the feature still owns which state is complete or
invalid and which copy and navigation apply.

The feature's CSS Module owns its `40rem` task measure, local gaps, action row,
and narrow action stacking. It consumes generated semantic and scale tokens
without introducing a feature palette.

## 8. Trace Localization Ownership

Visible messages live in
[server/i18n/en.json](https://github.com/sudosylabs/Proctor/blob/main/server/i18n/en.json)
under `webapp.reset_password.*` plus shared form message IDs. The generator
writes a typed catalog consumed through `message()`.

Run:

~~~sh
cd webapp
npm run i18n:generate
npm run i18n:check
~~~

The state machine selects complete message IDs. It does not concatenate a
sentence from fragments or combine a server-provided string with local copy.
The pending label uses the ellipsis character and remains meaningful when
reduced motion removes animation.

## 9. Prove the Browser Behavior

The hosted-access Playwright suite intercepts the completion operation and
proves:

- the fragment credential disappears from the URL before interaction;
- the request body contains the token and password but not confirmation;
- declared HTTP 204 produces the completion state;
- the replacement heading receives focus and the live region announces it;
- token and password values disappear from the rendered body;
- server-reported invalid credential produces the unusable-link terminal state;
- a missing credential is safe and initially does not steal focus;
- the route remains one-dimensional in dark mode at `390×844`;
- 200% zoom introduces no horizontal overflow; and
- the same scenarios execute in Chromium, Firefox, and WebKit.

Run the focused browser file across all configured projects:

~~~sh
cd webapp
npx playwright test tests/browser/hosted-access.spec.ts
~~~

Use a title or line filter only while iterating. Before handoff, run the whole
browser suite because changes to a shared field, task, shell, theme, or notice
can affect every hosted route.

## Apply the Pattern without Copying It

Another feature may not need a fragment credential, form, terminal
replacement, or initial request. Keep only the owners required by the real
states.

- A read-only status page may use a route loader and no form controls.
- A credential-free form has no fragment bootstrap or credential lifetime.
- A server-side validation result may remain a general form failure when it
  cannot safely identify one field.
- A recoverable unavailable state may use `TaskState` with retry rather than a
  form-feedback lane.
- A future authenticated product page may require a different shell proven by
  its own real consumers.

The invariant is that the server owns public and durable authority, generated
adapters carry reviewed contracts into the browser, and the feature owns one
bounded interaction state machine.
