# Change HTTP and OpenAPI

Proctor's public API has one human authoring system and several verified
consumers. Resource-oriented YAML modules under `server/openapi` own the wire
contract and reference prose. The compiler produces `server/openapi.json`;
runtime agreement tests, the webapp type generator, and the documentation site
consume that reviewed artifact.

Never edit `server/openapi.json` or generated endpoint pages by hand.

## Find the Existing Owner

Search by path or stable operation ID:

```sh
rg -n '/api/v1/exams|operationId: createExam' server/openapi/fragments
```

Choose the existing product-area directory and narrowest resource module.
Create another descriptive YAML file only when no existing resource is a
natural owner. Files are discovered recursively; there is no manifest to edit.

Definitions used by one resource stay in that resource file. Promote a schema,
parameter, request body, or response to a product-area `shared.yaml` only when
several resources in that area consume it. The root `shared.yaml` is for
genuinely cross-area definitions.

## Implement One Complete Operation

An operation change normally touches these surfaces together:

1. **Application capability** — typed command or query and result.
2. **HTTP resource** — strict request DTO, explicit domain mapping, typed
   result, and allowlisted public errors.
3. **Route catalog** — one explicit credential and assurance requirement.
4. **OpenAPI source** — exact path, method, schema, prose, examples, and Proctor
   extensions.
5. **Agreement tests** — route, authentication, DTO, success schema, and public
   error agreement.
6. **Consumer adapters** — regenerate webapp API types or update authored API
   recipes when the public contract requires it.

The HTTP Routing Kernel is sealed before serving. Add the resource to its
explicit production catalog; do not register routes through initialization,
expose router internals, or add a generic response-writer escape hatch.

## Trace the Sealed Route Catalog

The production route path is intentionally searchable:

```text
httpapi.New
  → productionResources
  → one cohesive <domain>Resource
  → publicRoute / principalRoute / sessionRoute / …
  → catalog validation and immutable dispatch
  → one application capability
```

The resource constructor declares typed paths, operations, credential
requirements, allowed public errors, body limits, idempotency, and any named
protocol-specific result. It retains only its narrow application capability.
It never retains the complete HTTP options, application facade, router, root
Store, platform, or concrete adapter.

The catalog rejects duplicate normalized method/path shapes, unknown parameter
kinds, invalid authentication requirements, and incomplete public-error
mappings before the server can accept traffic. Every entry point—including
the WebSocket upgrade—appears in this catalog.

## Keep Handlers Mechanical

An ordinary handler should be easy to review in one pass:

1. decode a bounded request into a transport-owned DTO;
2. parse canonical IDs and other wire values;
3. map them explicitly into one typed application command or query;
4. call one application capability with the immutable invocation; and
5. map the safe result into a response DTO.

Apply the body limit before decoding. JSON requests accept exactly one value,
reject unknown fields and trailing content, and distinguish omission, zero,
and explicit null with `Optional[T]` when the contract needs that distinction.
Only a named bounded extension object may accept unknown keys.

Domain models never double as request or response DTOs. An innocent field
added to a domain record must not silently become a new public field.

Ordinary operations return a typed status/body result and `error`. Redirects,
uploads, downloads, and upgrade transfer use reviewed named result types. The
WebSocket handshake is the sole raw-response exception because a successful
upgrade transfers connection ownership to the sibling transport.

## Declare Credential and Assurance Separately

Every route declares what establishes its principal: public, authenticated,
interactive Session, refresh credential, strong authentication, recent
reauthentication, or a composed requirement. Administrative permission is not
a route authentication class; the application use case evaluates it against
the current resource.

Cookie-authenticated unsafe requests also require the route’s CSRF proof.
Bearer and cookie sources cannot be mixed and resolved by precedence. Keep the
runtime declaration, OpenAPI `security`, and `x-proctor-auth` value in exact
agreement.

## Map Expected Failures Exhaustively

An expected application failure uses a stable dotted code with explicitly safe
fields. It contains no HTTP status, localized prose, request ID, SQL detail, or
stack trace. The transport maps only allowlisted codes to declared RFC 9457
Problem Details responses.

Unknown or undeclared errors become a generic correlated internal failure and
are logged once at the outer operational boundary. Never improvise a status
from an error string. The owning resource’s agreement test proves its complete
success schema and public-error set against OpenAPI.

Read [authorization, errors, and audit](./server/authorization-errors-audit.mdx)
before deciding whether a denied exact resource is safely forbidden or
concealed as not found.

## Design Collections and Cursors

New collections return an object with a non-null `items` array and optional
`next_cursor`. Unbounded collections use keyset pagination, not growing
offsets.

Cursors are opaque, versioned, bounded, and untrusted. Clients return them
unchanged. The shared envelope validates canonical encoding and object shape;
the resource owns the keyset fields, stable ordering, semantic validation, and
any compatibility window. Never include a private Workspace path, credential,
or unbounded filter in a cursor.

## Supply the Full Contract

Every operation has exactly one public product-area tag and all of the
following:

- concise imperative `summary`;
- substantive behavioral `description`;
- explicit OpenAPI `security`;
- `x-proctor-auth` matching the runtime route;
- `x-proctor-error-codes` matching declared responses;
- `x-proctor-idempotency` set to `none`, `optional`, or `required`;
- a purpose description for every parameter and request body; and
- a schema-valid synthetic request example for mutations, or an executable
  `x-codeSamples` example for bodyless and multipart mutations.

Public failures use RFC 9457 Problem Details and stable application codes.
Unknown application errors fail closed; do not turn an undeclared internal
error into an improvised public response.

Examples must never contain real Institutions, Users, Exams, answers,
credentials, email addresses, object keys, hostnames, or local paths. Use
clearly synthetic values and explicit credential placeholders.

## Build and Prove Agreement

Regenerate the reviewed artifact:

```sh
make -C server openapi-build
```

Review the `server/openapi.json` diff, then validate source-to-artifact drift:

```sh
make -C server openapi-check
```

Prove agreement with the registered HTTP surface:

```sh
make -C server openapi-agreement
```

For a reference-content or presentation change, also run:

```sh
cd docs/site
npm run audit:openapi
npm run test:openapi-audit
npm run test:openapi-reference
```

Finish with `make docs-check` when endpoint pages, product-area navigation, API
recipes, or reference presentation changed.

## Regenerate Browser Types

When a changed schema is consumed by the hosted webapp:

```sh
cd webapp
npm run api:generate
npm run api:check
```

The generated TypeScript schema is a consumer of the reviewed OpenAPI artifact.
Do not patch it to compensate for an incomplete source contract.

## Preserve Compatibility

The current public API is namespaced under `/api/v1`, but Proctor has not yet
made its first supported-release API commitment. During this pre-release
period, a contract can change in place only when the server, reviewed OpenAPI
artifact, agreement tests, and compatible clients move together. Do not create
a parallel version solely to preserve an old development contract.

After the first supported release, established meanings evolve additively
unless an explicit compatibility decision introduces another version and
migration path. Renaming a field, narrowing an accepted value, changing
concealment behavior, or removing a public error may be breaking even when Go
compilation succeeds.
