# Develop With Proctor

Proctor is one product repository with four independently versioned Go modules,
a server-hosted React application, and a separately built documentation site.
This guide turns those boundaries into a contribution path: start the product,
choose the owner of a change, use the nearest contract, and run checks in order
of cost.

<Maturity state="preview">
  The development environment, module checks, API compiler, browser gates, and
  documentation build are implemented. Project-wide contributor governance and
  the supported operating-system policy remain open and are called out where
  they affect a task.
</Maturity>

## Start Here

1. [Prepare the local environment](/developers/local-setup/) and run the
   production-shaped single-node lifecycle.
2. [Tour the repository boundaries](/developers/repository-boundaries/) before
   deciding where a change belongs.
3. Follow the workflow for the surface you are changing, then use the
   [verification ladder](/developers/testing/) before proposing the work.

## Choose the Work You Are Doing

| Goal | Start with | Finish with |
| --- | --- | --- |
| Change domain or server behavior | [Server workflow](/developers/server-workflow/) | Focused tests, server check, affected integration suite |
| Change a hosted browser flow | [Webapp workflow](/developers/webapp-workflow/) | Generated adapters, browser matrix, webapp check |
| Change cache, mail, or VFS behavior | [Reusable modules](/developers/reusable-modules/) | Module conformance, race, vet, workspace-independent build |
| Add or change an HTTP operation | [HTTP and OpenAPI](/developers/http-and-openapi/) | OpenAPI build, agreement, reference audit |
| Change durable data or SQL | [Persistence workflow](/developers/persistence/) | Store conformance, migration and PostgreSQL integration tests |
| Change public or maintainer documentation | [Documentation workflow](/developers/documentation/) | Affected generators, docs check, architecture gate |
| Prepare work for review | [Contribution checklist](/developers/contribution-checklist/) | Clean diff and the highest relevant repository gate |

## Keep the Authority in One Place

Public guides explain tasks and consequences. The OpenAPI YAML modules own the
public HTTP contract. Component contracts and module READMEs own non-obvious
behavior at their boundary. Code, tests, configuration, and command help remain
the authority for implementation detail that can be discovered directly.

When a change alters more than one of those authorities, update them together.
Do not solve drift by copying the same inventory into several documents.

## Four Rules That Prevent Expensive Mistakes

1. **Choose ownership before abstraction.** Add a package or interface only
   for a stable responsibility with a real consumer.
2. **Keep policy inward.** HTTP, WebSocket, SQL, Redis, SMTP, VFS, Memberlist,
   and execution-host adapters do not own business rules.
3. **Commit before effects.** Durable state commits before cache invalidation,
   cluster fan-out, realtime publication, execution projection, or delivery.
4. **Verify the smallest honest surface first.** A focused test gives fast
   feedback; the relevant module and product gates prove the complete boundary.
