# Develop the Proctor Server

The Proctor server is organized around ownership, not around framework layers.
A change starts with a user-visible or operational behavior, crosses only the
boundaries that behavior needs, and finishes with evidence at every changed
boundary. The aim is not to create a model, service, Store, and route for
symmetry. The aim is to make one coherent behavior true.

This manual is for contributors who already write Go but do not yet know where
Proctor keeps policy, durable guarantees, transport rules, or runtime
ownership. Read it in order for a first server change; return to the focused
chapters during review.

## The Placement Rule

Ask who must remain correct if the transport, database, cache, or application
node changes.

| Decision | Owner |
| --- | --- |
| Whether one value or state transition is locally valid | `server/model` |
| Whether the current actor may perform the use case, and in what order | `server/app` or one justified application child |
| What must commit atomically and which races have one winner | A named contract under `server/store` |
| How PostgreSQL locks, constrains, retries, and commits it | `server/store/sqlstore` |
| How an HTTP request becomes a typed command and a safe response | `server/httpapi` |
| What the public wire contract promises | Human-owned YAML under `server/openapi` |
| How a WebSocket connection sequences, replays, and sheds load | `server/websocket` |
| How portable cache, mail, or VFS mechanics work | The corresponding independent module under `packages` |
| Which concrete adapters run and who closes them | Module-root `server.New` and `platform.Service` |

If two rows appear to own the same decision, the design is not finished. For
example, transport owns strict JSON decoding, while the domain owns the local
validity of the decoded value. PostgreSQL may enforce the invariant again for
concurrency, but it does not become the author of business policy.

## Work One Vertical Slice at a Time

Before editing, write a short boundary map in your notes:

```text
Behavior:        what changes for a User or operator?
Domain term:     which canonical concept and transition are involved?
Principal:       who or what invokes the behavior?
Action/resource: what current authority is required?
Durable fact:    what must survive process loss?
Public shape:    which route, DTO, errors, and examples change?
Effects:         what happens only after commit?
Evidence:        which focused, conformance, integration, and broad tests prove it?
```

Then inspect the current code and tests. Do not create an interface until its
consumer and complete need are known. Do not create a child package until the
responsibility has enough stable structure to survive deletion of its current
callers. Do not add a route until the application behavior exists without
HTTP.

## Preserve the Non-Negotiable Order

For an actor-sensitive mutation, the usual chronology is:

1. Establish a bounded immutable invocation from the transport proof.
2. Resolve the canonical resource and current authority.
3. Authorize immediately before expensive work or mutation.
4. Prepare safe audit intent and, when required, command idempotency.
5. Commit the durable state, required audit, retained outcome, Job, or mail
   intent through one named Store operation.
6. Publish cache, cluster, WebSocket, execution, or other reconstructible
   effects only after commit.
7. Translate the result into an allowlisted public response.

Not every read or mutation uses every step. The omission must follow the
owning contract, not convenience in a handler.

## Know the Sources of Truth

This manual explains how to work. It deliberately does not duplicate live
inventories. Use these authorities while implementing:

- the [server module guide](https://github.com/sudosylabs/Proctor/blob/main/server/README.md)
  for construction, running, and verification;
- the [HTTP transport contract](https://github.com/sudosylabs/Proctor/blob/main/server/httpapi/CONTRACT.md)
  for exact routing and mapping guarantees;
- the [OpenAPI authoring guide](https://github.com/sudosylabs/Proctor/blob/main/server/openapi/README.md)
  for the human-first public contract workflow;
- the [cluster guarantees](https://github.com/sudosylabs/Proctor/blob/main/server/cluster/GUARANTEES.md)
  for exact delivery and recovery behavior; and
- code, tests, configuration examples, and command help for discoverable
  implementation detail.
